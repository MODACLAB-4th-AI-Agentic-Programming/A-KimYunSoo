### 1. Blinn-Phong 스페큘러 조명 (`3db5bbd`)

기존 Lambert 조명에 Blinn-Phong 스페큘러를 추가했다.

**핵심 변경:**
- `cbPerObject`에 `specPower` 필드 추가, 16바이트 패딩 정렬 (224 → 240 bytes)
- `POM_PS.hlsl`: Half-vector `H = normalize(viewDir + L)` 기반 스페큘러 계산
- `NdotL`로 스페큘러를 마스킹해 빛이 닿지 않는 면에 하이라이트 제거
- ImGui에 Specular Power 슬라이더 추가 (1.0 ~ 256.0)

```hlsl
float3 H    = normalize(viewDirWS + L);
float NdotH = saturate(dot(normalWS, H));
float spec  = pow(NdotH, gSpecPower);
float3 lit  = diffuse.rgb * (NdotL * 0.85 + 0.15)
            + float3(1,1,1) * spec * 0.6 * NdotL;
```

**Blinn-Phong vs Phong:** 반사 벡터(R) 대신 Half-vector(H)를 사용해 연산이 더 빠르고, 넓은 시야각에서 더 자연스러운 결과를 낸다.

### 2. Shadow Mapping 2-Pass 렌더링 (`5541856` ~ `3fd8721`)

광원 시점에서 깊이를 먼저 렌더링하고, 메인 패스에서 그 깊이맵을 참조해 그림자를 계산하는 2-Pass 구조를 구현했다.

**구현 순서:**
1. `Shadow_VS.hlsl` — 광원 기준 MVP 변환만 수행하는 버텍스 셰이더
2. `BuildShadowResources()` — 1024×1024 깊이 텍스처, DSV, SRV, 샘플러, RS, CB 생성
3. `cbPerObject`에 shadow 필드 추가 (`gLightViewProj`, `gShadowBias`, `gShadowIntensity`, `gPCFKernel`)
4. `Update()`에 광원 카메라(LookAtLH) 행렬 계산
5. `RenderShadowPass()` — 광원 뷰포트로 깊이만 렌더링
6. `RenderMainPass()` — 기존 렌더링 + 그림자 팩터 적용
7. `POM_PS.hlsl`에 `CalcShadowFactor()` PCF 함수 추가

**PCF (Percentage Closer Filtering):**

단순히 깊이 비교만 하면 그림자 경계가 픽셀 단위로 딱딱하게 나온다.  
PCF는 주변 텍셀 N×N을 샘플링해 평균을 내서 부드러운 경계를 만든다.

```hlsl
for (int y = -radius; y <= radius; ++y)
for (int x = -radius; x <= radius; ++x)
    shadow += gShadowMap.SampleCmpLevelZero(
        gShadowSamp, uv + float2(x, y) * texelSize, depth);
return lerp(1.0 - gShadowIntensity, 1.0, shadow / total);
```

ImGui에서 PCF Kernel 크기(1×1, 3×3, 5×5)를 실시간으로 바꿀 수 있다.

### 4. POM 아티팩트 수정 — 이진 탐색 정밀화

**문제:** Height Scale을 높이면 깊은 홈에서 여러 겹이 중첩되는 시각적 아티팩트 발생

**원인 분석:**

POM 레이마칭은 표면과 교차하는 레이어를 찾은 뒤 교차점을 추정해야 한다.  
이전 구현은 교차 직전/직후를 **선형 보간**했는데, 높이맵이 급격히 변하는 깊은 홈에서는 선형 근사가 크게 빗나간다.

```
높이맵 단면 예시
1.0 │████     ████
0.0 │    ▔▔▔▔
         ↑ 교차 직전  ↑ 교차 직후
         선형 보간 → 실제 교차점과 크게 어긋남
```

**해결: 이진 탐색(Binary Search) 정밀화**

교차 구간 `[prevUV, currentUV]`을 8번 이분해 실제 교차점에 수렴시킨다.  
선형 보간은 높이 프로파일이 선형이라고 가정하지만, 이진 탐색은 가정 없이 수렴한다.

```hlsl
// 1단계: 교차 구간 탐색 (64 layers)
for (int i = 0; i < 64; i++) {
    if (currentDepth >= h) break;
    prevUV = currentUV; prevDepth = currentDepth;
    currentUV -= uvStep; currentDepth += layerDepth;
    h = gHeightMap.Sample(gSampler, currentUV).r;
}

// 2단계: 이진 탐색으로 교차점 정밀화 (8회 → 256배 정밀도)
for (int j = 0; j < 8; j++) {
    float2 midUV    = (prevUV + currentUV) * 0.5;
    float  midDepth = (prevDepth + currentDepth) * 0.5;
    float  midH     = gHeightMap.Sample(gSampler, midUV).r;
    if (midDepth < midH) { prevUV = midUV; prevDepth = midDepth; }
    else                 { currentUV = midUV; currentDepth = midDepth; }
}
return (prevUV + currentUV) * 0.5;
```

## AI를 어떻게 활용했나

### 활용 방식

이번 작업 전반에 걸쳐 **Claude Code (claude-sonnet-4-6)** 를 사용했다. 단순한 코드 생성 요청이 아니라 다음과 같은 방식으로 상호작용했다.

#### 1. 문제 정의 → 원인 분석 → 구현 흐름

"Height Scale 높이면 겹쳐 보인다"는 현상을 말하면, AI가 원인을 진단하고 해결 방향을 제안했다.

- **첫 번째 시도**: 선형 보간 추가 → 계단 아티팩트 개선
- **두 번째 시도**: 여전히 문제 있다고 피드백 → AI가 선형 보간의 한계를 분석하고 이진 탐색으로 전환

이처럼 **"아직 문제 있다"** 고 피드백하면 AI가 스스로 이전 접근법의 한계를 재분석하고 더 나은 방법을 제시했다.

#### 2. 전체 코드 컨텍스트 이해

AI는 D3DApp.h, D3DApp.cpp, Sphere.h, Sphere.cpp, Camera.h, POM_PS.hlsl 등을 읽고 전체 구조를 파악한 뒤 변경 범위를 최소화했다.

예: Quad 추가 시, 카메라 위치(`z = -3`, LH 좌표계), 래스터라이저 설정(`FrontCounterClockwise = FALSE`), 기존 Sphere.cpp의 구조를 모두 고려해 일관된 코드를 작성했다.

#### 3. 빌드 오류 자체 진단

Quad.cpp를 작성한 뒤 `.vcxproj`에 추가하지 않아 링커 오류가 발생했다. AI가 오류 메시지를 보고 `.vcxproj`에 `<ClCompile>`과 `<ClInclude>` 항목을 직접 추가해 해결했다.

#### 4. 직접 수정하지 않은 것

- 셰이더 알고리즘의 수학적 검증 (Normal = T×B 등) — AI가 계산 후 사용자가 결과 확인
- 어떤 메쉬 모드가 필요한지 — 사용자가 요구사항 결정
- Height Scale 한계값 — 사용자가 직접 실행해 아티팩트 확인 후 피드백

### 느낀 점

AI는 **"뭘 만들지"** 를 정하는 게 아니라 **"어떻게 만들지"** 를 빠르게 처리한다.  
특히 DirectX API의 반복적인 보일러플레이트(버퍼 생성, 스테이지 바인딩 등)를 자동화해서 알고리즘에 집중할 수 있었다.

반면 POM 아티팩트처럼 **"무엇이 문제인지"** 를 정확히 설명할수록 더 빠르게 해결됐다.  
"뭔가 이상하다" < "겹쳐 보인다" < "깊은 홈에서 여러 겹 중첩" 순으로 AI의 진단 정확도가 올라갔다.
